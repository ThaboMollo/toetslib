1. Introduction

toetsLib is an AI-powered CLI tool that analyzes React repositories and automatically generates comprehensive Playwright end-to-end test suites.

Instead of writing tests by hand, you point toetsLib at your project and it:

  • Parses your source code to understand routes, forms, API calls, and auth patterns
  • Starts your app and crawls it with a headless browser to discover real UI elements
  • Uses Claude AI to generate Playwright tests with Page Object Models
  • Runs the generated tests and produces a diagnostic report with fix instructions

The output is a complete e2e/ directory with playwright.config.ts, page objects, fixtures, test specs, and a DIAGNOSTIC.md that tells your team exactly what to fix if any tests fail.

2. Installation

Prerequisites

  • Node.js 18 or later
  • npm (or yarn, pnpm, bun)
  • ANTHROPIC_API_KEY environment variable — required for test generation

Install from Source

git clone <repo-url> toetslib
cd toetslib
npm install
npx turbo build

Run the CLI

# Direct execution
node apps/cli/dist/index.js --help

# Or link globally
cd apps/cli && npm link
toetslib --help

Set Your API Key

export ANTHROPIC_API_KEY="sk-ant-api03-..."
Note: The analyze and crawl commands work without an API key since they don't use AI. Only generate and validate require it.

3. Quick Start

Generate a full Playwright test suite in one command:

toetslib generate ./my-react-app

That's it. Your tests land in ./e2e/ by default.

Step-by-Step First Run

# 1. Check what toetsLib detects in your project
toetslib analyze ./my-app --json

# 2. See what the browser finds (starts dev server)
toetslib crawl ./my-app --verbose

# 3. Generate tests without running them
toetslib generate ./my-app --no-validate

# 4. Generate tests AND run them with diagnostics
toetslib generate ./my-app --verbose

4. How It Works — The 5-Stage Pipeline

1. INGEST
→
2. ANALYZE
→
3. CRAWL
→
4. GENERATE
→
5. VALIDATE

Stage 1: Ingest

Reads your project and detects its configuration automatically.

DetectionMethod
Package managerLock file check (package-lock.json → npm, yarn.lock → yarn, etc.)
FrameworkDependencies in package.json (vite + plugin-react → react-vite, next → nextjs)
Dev commandReads scripts.dev or scripts.start
Dev portParsed from vite.config.js / next.config.js
Source directoryChecks for src/, app/, pages/
Workspace rootWalks up directory tree to find workspace package.json

Stage 2: Analyze (Static Code Analysis)

Parses your source files using Babel AST to understand the application structure.

  • Routes: React Router declarations, route arrays, constant references, file-based routing
  • Components: Maps which page components render on which routes, including child components
  • Forms: Detects form fields from both native HTML elements and custom components (InputField, MoneyInput, SelectField, etc.)
  • API calls: Extracts endpoints from axios, fetch, TanStack Query hooks (useQuery, useMutation)
  • Auth patterns: Identifies auth contexts, route guards, login redirects, and trial/guest modes

Stage 3: Crawl (Live Browser)

Starts your dev server and visits your app with a headless Playwright browser.

  • Visits every discovered route
  • Takes screenshots at 3 viewport sizes (mobile 375px, tablet 768px, desktop 1280px)
  • Finds all interactive elements with their selectors
  • Records the navigation graph (which pages link to which)
  • Logs console errors and failed network requests
  • Handles login with provided credentials (if configured)

Stage 4: Generate (AI-Powered)

Uses Claude AI to produce Playwright test code in three passes:

PassInputOutput
1. Test PlanFull AppMap summaryStructured JSON: which pages get tests, what categories, test names
2. Page ObjectsPer-page: crawl data + screenshot + form fieldsTypeScript Page Object Model (.page.ts) per page
3. Test CodeTest plan + page object codePlaywright spec files (.spec.ts) using page objects
Screenshots are sent to the AI so it can "see" each page while writing tests. This produces much better selectors than text-only analysis.

Stage 5: Validate (Diagnostic)

Runs the generated tests and produces a diagnostic report.

  • Executes all tests via Playwright
  • Parses failures by category: selector, timeout, assertion, navigation
  • Writes DIAGNOSTIC.md with step-by-step fix instructions per failure
  • Writes .toetslib-report.json for machine consumption

6. Configuration

Create a .toetslib.json or toetslib.json in your project root:

{
  "devCommand": "npm run dev",
  "devPort": 5173,
  "baseUrl": "http://localhost:5173",
  "auth": {
    "strategy": "form",
    "loginUrl": "/login",
    "fields": {
      "email": "test@example.com",
      "password": "secret"
    },
    "submitSelector": "button[type=submit]"
  },
  "exclude": ["/admin/*"],
  "outputDir": "./e2e",
  "maxHealCycles": 3
}
FieldTypeDescription
devCommandstringDev server start command. Auto-detected if not set.
devPortnumberDev server port. Auto-detected from config files.
baseUrlstringFull base URL. Built from port if not set.
authobjectAuthentication config (see Section 7).
excludestring[]Route patterns to skip (glob syntax).
outputDirstringWhere to write tests. Default: ./e2e
maxHealCyclesnumberDiagnostic retry cycles. Default: 3

Priority Order

When the same setting appears in multiple places:

  1. CLI flags (highest)
  2. Config file (.toetslib.json / toetslib.json)
  3. Auto-detected values (lowest)

      "password": "secret"
    },
    "submitSelector": "button[type=submit]"
  }
}

Trial / Guest Mode

If your app supports unauthenticated access (e.g., trial mode with localStorage-backed data), toetsLib detects this automatically. The analyzer identifies:

  • localStorage usage for data persistence
  • Conditional rendering based on isAuthenticated
  • Feature restrictions for unauthenticated users

No credentials needed for trial-mode testing.

Security: Avoid committing real credentials to .toetslib.json. Use CLI flags or environment variables for sensitive data.

8. Generated Output

After running toetslib generate, your output directory contains:

e2e/ ├── playwright.config.ts # Auto-configured for your project ├── pages/ # Page Object Models │ ├── landing.page.ts │ ├── payroll.page.ts │ ├── employee-form.page.ts │ └── ... ├── fixtures/ # Test data and setup │ ├── base.fixture.ts # Extended Playwright fixtures │ ├── test-data.ts # Mock form data (context-aware) │ └── auth.setup.ts # Login flow (if auth configured) ├── tests/ # Test spec files │ ├── navigation.spec.ts │ ├── landing.spec.ts │ ├── employee-create.spec.ts │ └── ... ├── DIAGNOSTIC.md # Human-readable fix instructions └── .toetslib-report.json # Machine-readable results

Page Objects

Each page gets a Page Object Model with typed selectors and helper methods. Selectors are prioritized for stability:

  1. page.getByTestId() — data-testid attributes (most stable)
  2. page.getByRole() — ARIA roles
  3. page.getByLabel() — form labels
  4. page.getByText() — visible text
  5. page.locator() — CSS selectors (last resort)

Test Categories

CategoryWhat It Tests
SmokePage loads, key elements visible, no console errors
Happy pathCore user flows end-to-end (create, edit, submit)
ValidationForm errors on bad/missing input
Edge casesEmpty states, loading states, boundary conditions
ResponsiveLayout at mobile (375px), tablet (768px), desktop (1280px)
NavigationAll links work, routing correct, mobile menu

Test Data

The test-data.ts fixture generates context-aware test data based on detected form fields. For South African apps, this includes SA ID numbers, ZA phone formats, and local addresses.

9. Diagnostic Reports

Instead of auto-fixing failures, toetsLib produces a diagnostic report that tells your team exactly what's wrong and how to fix it.

DIAGNOSTIC.md

A human-readable report with:

  • Summary table (total, passed, failed, pass rate)
  • Failures grouped by category
  • Step-by-step fix instructions per failure
  • Actionable recommendations

Failure Categories

CategoryWhat It MeansTypical Fix
SelectorElement not found in DOMAdd data-testid attributes, update locator to use getByRole
TimeoutElement didn't appear in timeCheck if backend APIs are running, add proper wait conditions
AssertionContent doesn't match expectedCheck formatting (currency, dates), use flexible matchers
NavigationPage failed to load/redirectCheck route config, auth requirements, HTTPS settings

Machine-readable report for CI/CD integration:

12. CI/CD Integration

GitHub Actions

name: E2E Tests
on: [push]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'

      - name: Install toetsLib
        run: |
          cd toetslib && npm install && npx turbo build

      - name: Generate tests
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          toetslib generate . --output ./e2e --no-validate

      - name: Run tests
        run: |
          cd e2e && npx playwright install chromium
          npx playwright test

      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: test-results
          path: |
            e2e/DIAGNOSTIC.md
            e2e/.toetslib-report.json
            e2e/test-results/

Quality Gate

# Fail CI if pass rate is below threshold
PASS_RATE=$(jq -r '.summary.passRate' e2e/.toetslib-report.json | tr -d '%')
if [ "$PASS_RATE" -lt 80 ]; then
  echo "Pass rate $PASS_RATE% is below 80% threshold"
  exit 1
fi

13. Troubleshooting

"Framework not detected"

Ensure package.json lists React and a bundler (vite, react-scripts, next) as dependencies. Use .toetslib.json to manually specify devCommand and devPort.

"Dev server failed to start"

  • Check that npm run dev works when run manually
  • For monorepos, toetsLib auto-detects the workspace root and installs from there
  • Check if the port is already in use: lsof -ti :PORT

"No routes found"

Run toetslib analyze ./my-app --json --verbose to see what the parser finds. Routes may use patterns the AST parser doesn't recognize yet.

"ANTHROPIC_API_KEY not set"

The generate command requires an API key. Set it: export ANTHROPIC_API_KEY="sk-ant-..."

"Tests fail after generation"

Check DIAGNOSTIC.md for categorized failure analysis with fix instructions. Most common issues are selector mismatches (add data-testid attributes) or missing backend APIs (run the backend or mock responses).

14. Architecture

toetsLib is a Turborepo monorepo with focused packages:

PackagePurpose
@toetslib/cliCLI entry point with 4 commands (commander)
@toetslib/corePipeline orchestrator, AppMap types (15 interfaces)
@toetslib/sharedLogger, file utilities, Claude API client with prompt caching
@toetslib/ingestFramework detection, dev server management
@toetslib/analyzerBabel AST-based static code analysis
@toetslib/crawlerHeadless Playwright browser crawling
@toetslib/generator3-pass AI test generation via Claude API
@toetslib/validatorTest runner and diagnostic report writer

AppMap — The Central Data Model

A single TypeScript object flows through all 5 pipeline stages. Each stage enriches it with its findings:

  • Stage 1: project (framework, port, dev command)
  • Stage 2: routes, forms, apiCalls, auth, components
  • Stage 3: pages, interactions, screenshots, navigationGraph
  • Stage 4: testPlan + files written to disk
  • Stage 5: results + diagnostic report

AI Strategy

The LLM client uses Anthropic's prompt caching (cache_control: { type: "ephemeral" }) on the system prompt. Within the 5-minute TTL, all per-page generation calls reuse the cached system prompt, reducing cost and latency.

Screenshots are sent as images to the AI during page object generation, so the model can "see" the actual page layout while writing selectors and test code.
